## Step 3 — Write the plan
Write the full markdown plan to {{PLAN_OUTPUT_PATH}}. The plan MUST use EXACTLY this structure (a machine parses it):

```
# <goal in one line>

## T1: <title>
- [ ] <one single checkbox line, this task's work>
Acceptance: <what "done" means, concretely>
Verify: <the check that proves it — test/command/observable>

## T2: <title>
- [ ] ...
Acceptance: ...
Verify: ...
```

Strict rules the parser enforces:
- Each task heading is `## T<n>: <title>` with a STABLE unique id (`T1`, `T2`, …). No duplicate ids.
- Exactly ONE `- [ ]` line per task, immediately under the heading. Never more.
- `Acceptance:` and `Verify:` lines are required per task. No empty task body.
- Tasks are independently implementable in the given order.

Other rules:
- Do NOT tick checkboxes — leave every box `- [ ]`. Completion is recorded by the harness in its own
  state, NOT by editing this file. The `- [ ]` boxes stay open forever in `plan.md`.
- Keep the plan minimal and concrete. No speculative scope.
- Write ONLY to {{PLAN_OUTPUT_PATH}} or {{QUESTIONS_PATH}} — do not modify code, config, {{CURRENT_PLAN_PATH}},
  or any other file. {{CURRENT_PLAN_PATH}} (when present) is READ-ONLY input; the harness renames your
  {{PLAN_OUTPUT_PATH}} into place only after it validates.
- On revision, read {{CURRENT_PLAN_PATH}} and write the full revised plan to {{PLAN_OUTPUT_PATH}}; preserve
  stable task ids where a task's intent is unchanged. Changing a task's meaning must change its id or be an
  explicit new task.

After writing {{PLAN_OUTPUT_PATH}} (or {{QUESTIONS_PATH}}), STOP immediately.
